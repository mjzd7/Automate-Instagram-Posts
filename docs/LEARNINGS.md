# Failure register & self-improvement loop

> Referenced from `AGENTS.md`. This file is how the contract improves itself instead of staying static — read the "Promotion trigger" section even if you're only here to log one row.

## 15. Skill distillation & failure register

When a gate fails in prod-like ways, or the same slop repeats:

1. Reproduce with a test or semgrep rule when possible.
2. Minimal fix.
3. Log a row below **immediately** — don't wait for end-of-task DISTILL, log while context is freshest.
4. Only then consider a new skill/rule.

Skills that never catch real issues are candidates for deletion — do not hoard ceremony.

## Detection triggers (log the moment you see one of these, not after)

**Corrections** — the user is telling you a rule was wrong or missing:
- "No, that's not right..." / "Actually, it should be..." / "You're wrong about..." / "That's outdated..."

**Errors** — the environment is telling you something broke:
- Command returns non-zero exit code
- Exception or stack trace
- Unexpected output or behavior that took investigation to explain
- Timeout or connection failure on something assumed to work

**Knowledge gaps**:
- User provides information you didn't have and should have checked
- Documentation you referenced turned out to be outdated
- A tool/API behaved differently than assumed

A one-off typo or a mistake with an obvious, non-generalizable cause does **not** need a row — this register is for patterns, not every slip.

## Promotion trigger — how logging becomes a real rule change

Logging a row is not the end state; an unpromoted register is just a diary. When the **same root cause** appears in **2 or more rows** (match on the "Root cause" column, not surface symptom):

1. Stop and draft a concrete proposed change: which file (`AGENTS.md` or a `docs/*.md`), which section, exact wording.
2. Present the proposal to the user for approval — **never apply it silently**. This is the same rule as everywhere else in this contract: no silent doctrine changes (hard block §11.14's spirit applies here too).
3. On approval, make the edit and mark the register rows' "Distilled to" column with the section that now covers it.
4. On rejection, leave the rows as-is — they still document the pattern even if no rule was added.

This is what makes the contract self-improving rather than just self-documenting: the register isn't a graveyard, it's a queue of pending proposals that fires automatically at N=2, not whenever someone happens to reread this file.
